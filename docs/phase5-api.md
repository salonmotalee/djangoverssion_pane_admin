# API فاز پنجم دماوند

تمام مسیرها زیر `/api/organizations/{slug}/` قرار دارند. نشست مرکزی، نشست مدیر مجموعه و نشست مراقب سه فضای مستقل‌اند. `slug` فقط نشانی مجموعه است؛ مجوز از نشست معتبر، عضویت و سالن‌های تخصیص‌یافته در سرور استخراج می‌شود. تمام درخواست‌های نوشتنی به CSRF نیاز دارند: ابتدا `GET /api/auth/csrf/` و سپس ارسال `X-CSRFToken` همراه کوکی‌ها. انقضای اشتراک مانع دسترسی نیست.

تاریخ API به شکل `YYYY-MM-DD` میلادی و زمان‌ها به شکل استاندارد ذخیره می‌شوند. محاسبات روز کاری با `Asia/Tehran` انجام می‌شوند؛ رابط تاریخ شمسی نمایش می‌دهد. شناسهٔ مجموعه، مراقب مسئول، مالک ثبت و timestamp را از کلاینت قبول نکنید.

## حساب مراقب

| روش و مسیر | مجوز | کاربرد |
| --- | --- | --- |
| `GET supervisor-access/{personnel_id}/` | مدیر همان مجموعه | وضعیت ورود، شمارهٔ نرمال‌شده و سالن‌ها |
| `PUT supervisor-access/{personnel_id}/` | مدیر همان مجموعه | `{enabled, password?}`؛ فعال/غیرفعال یا بازنشانی رمز |
| `POST supervisor/login/` | عمومی، با CSRF و محدودسازی تلاش | `{username, password}`؛ نام کاربری شمارهٔ همراه مراقب |
| `GET supervisor/me/` | مراقب | هویت، مجموعه و سالن‌های مجاز |
| `GET supervisor/profile/` | مراقب | پروفایل |
| `PATCH supervisor/profile/` | مراقب | `{current_password, new_password}`؛ تغییر امن رمز |
| `POST supervisor/logout/` | مراقب | پایان نشست مراقب |

پروندهٔ مراقب (`operations.Supervisor`) مستقل از حساب ورود (`staff.SupervisorAccount`) است. شمارهٔ کارکنان غیر‌یکتا می‌ماند، اما فقط یک حساب فعال برای هر شماره در هر مجموعه مجاز است. یک شماره در مجموعه‌های مختلف مجاز است. رمز هش می‌شود و مقدار آن در هیچ پاسخ API برگردانده نمی‌شود. غیرفعال‌سازی، بایگانی، تغییر هویت یا رمز باعث ابطال نشست‌های قبلی می‌شود. مدیریت سالن‌ها از API موجود `supervisors/{id}/` انجام می‌شود و دسترسی در هر درخواست دوباره بررسی می‌شود.

## شیفت و برنامه

| روش و مسیر | کاربرد |
| --- | --- |
| `GET/POST work-shifts/` | فهرست/ساخت شیفت با `{name,start_time,end_time,is_active}` |
| `GET/PATCH/DELETE work-shifts/{id}/` | مشاهده/ویرایش/غیرفعال‌سازی شیفت |
| `GET schedule/?week_start=YYYY-MM-DD` | هفتهٔ شنبه تا جمعه، اطلاعات سالن/شیفت/مراقب و تعارض‌ها |
| `POST schedule/preview/` | پیش‌نمایش `{assignments:[{date,hall,shift,supervisor}],remove_ids:[]}` |
| `POST schedule/copy-preview/` | پیش‌نمایش کپی هفته یا تکرار الگو در ماه شمسی |
| `POST schedule/apply/` | اعمال انتخاب‌های مدیر با توکن پیش‌نمایش |
| `GET supervisor/schedule/?week_start=YYYY-MM-DD` | برنامهٔ متعلق به مراقب و سالن‌های مجاز او |

در کپی هفته، بدنه شامل `{mode:"week", source_week, target_week}` است؛ تاریخ‌ها شنبه‌اند. در تکرار ماه، `{mode:"month", source_week, jalali_year, jalali_month}` ارسال می‌شود. فقط روزهای داخل ماه مقصد تولید می‌شوند؛ هفته‌های ناقص و اسفند کبیسه محاسبه می‌شوند.

پاسخ پیش‌نمایش شامل `token`، `revision`، `rows`، `removals`، `conflicts` و `summary` است. `revision` برنامه fingerprint متنی و `revision` هر ثبت حضور‌وغیاب عددی است. هر ردیف `index` و وضعیت `new/existing/duplicate/invalid` دارد. خطای ردیف نامعتبر در `error` و تفاوت ساعت الگوی قبلی با تعریف فعلی در `times_changed`، `source_start_time` و `source_end_time` مشخص می‌شود. `GET schedule/audit/` سابقهٔ برنامهٔ همان مجموعه را برمی‌گرداند. بدنهٔ اعمال:

```json
{
  "token": "توکن برگشتی از پیش‌نمایش",
  "actions": [{"index": 0, "action": "add", "replace_ids": []}],
  "remove_ids": [],
  "confirm_conflicts": false,
  "override_reason": ""
}
```

اقدام‌ها `add/preserve/replace/skip` هستند. هیچ داده‌ای بدون انتخاب صریح حذف یا جایگزین نمی‌شود. تعارض زمانیِ یک مراقب، حتی بین دو سالن متفاوت، هشدار و تأیید مدیر می‌خواهد. قبل از اعمال، برنامه و مجوزها دوباره زیر قفل تراکنش بررسی می‌شوند؛ پیش‌نمایش قدیمی با خطای `409` رد می‌شود. زمان‌های برنامه به‌صورت snapshot نگه‌داری می‌شوند تا ویرایش تعریف شیفت تاریخچه را بازنویسی نکند.

## ورود و خروج

| روش و مسیر | کاربرد |
| --- | --- |
| `GET supervisor/dashboard/` | سالن‌ها، حضور فعلی، حضور‌وغیاب و برنامهٔ امروز/آینده |
| `GET supervisor/halls/` | سالن‌های مجاز همراه پارت‌ها |
| `GET supervisor/students/?hall=&search=&page=` | دانش‌آموزان و وضعیت حضور با صفحه‌بندی |
| `GET supervisor/presence/?student=&hall=&page=` | تاریخچهٔ زمانی ورود و خروج |
| `POST supervisor/presence/` | `{student,kind:"entry"}` یا `{student,kind:"exit"}` |

timestamp در سرور تولید می‌شود. حضور فعلی از آخرین رخداد واقعی به دست می‌آید؛ ورود/خروج متوالی تکراری رد می‌شود. تراکنش با انتقال دانش‌آموز و تغییر مجوز سالن هماهنگ است. نام و شناسهٔ سالن تاریخی در رخداد حفظ می‌شوند.

## حضور‌وغیاب

| روش و مسیر | کاربرد |
| --- | --- |
| `GET supervisor/attendance/?hall=&date=&session=` | پارت‌ها، roster و ثبت‌های قابل مشاهده همراه `can_edit` |
| `POST supervisor/attendance/bulk/` | ثبت دستی گروهی `{hall,date,session,records:[{student,status,revision?}]}` |
| `POST supervisor/attendance/preview/` | `{hall,date,session}`؛ محاسبهٔ وضعیت از بازه‌های تاریخی ورود/خروج |
| `POST supervisor/attendance/automatic/` | `{preview_token,students:[ids]}`؛ ثبت انتخاب‌های مجاز پس از پایان پارت |
| `GET attendance/?hall=&date=&session=` | نظارت مدیر بر ثبت‌های مجموعه |
| `POST attendance/corrections/` | اصلاح مدیر `{records:[{id,status,revision}],reason}` |

وضعیت‌ها `present/absent/late` هستند. حضور در آغاز پارت ⇒ حاضر؛ اولین ورود بعد از شروع و پیش از پایان ⇒ تأخیر؛ نبود بازهٔ هم‌پوشان ⇒ غایب. خروج زودهنگام در `early_departure` و `departed_at` ذخیره می‌شود و وضعیت اصلی را عوض نمی‌کند. چند ورود و خروج در همان پارت بر اساس بازه‌ها بررسی می‌شوند.

پیش‌نمایش پارت در حال اجرا `provisional:true` است و ثبت نهایی خودکار مجاز نیست. ثبت نهایی محاسبات و وضعیت داده‌ها را در سرور دوباره بررسی می‌کند؛ نتیجهٔ ارسالی کلاینت منبع تصمیم نیست. ثبت دستی هرگز با محاسبهٔ خودکار بی‌صدا جایگزین نمی‌شود.

`revision` برای جلوگیری از بازنویسی هم‌زمان الزامی است. مالک اولیهٔ هر ثبت، مراقب ایجادکننده است و فقط همان مراقب تا ۴۸ ساعت پس از `created_at` اجازهٔ ویرایش دارد. ویرایش این مهلت را تمدید نمی‌کند. مراقب دیگرِ مجاز همان سالن فقط می‌تواند بخواند. اصلاح مدیر همیشه به دلیل کوتاه نیاز دارد و audit شامل مدیر، مراقب اولیه، مقدار قبلی و جدید و زمان ثبت می‌شود؛ مالک و زمان ایجاد تغییر نمی‌کنند. عملیات گروهی اتمیک است و یک ردیف غیرمجاز مانع اعمال کل درخواست می‌شود.

## خطاها و محدودیت‌ها

- `400`: دادهٔ نامعتبر، تکرار رخداد یا انتخاب نامعتبر.
- `401`: نشست نامعتبر/منقضی؛ ورود دوباره لازم است.
- `403/404`: نبود مجوز مجموعه یا سالن؛ شناسهٔ خارجی دسترسی ایجاد نمی‌کند.
- `409`: داده یا پیش‌نمایش تغییر کرده است؛ دادهٔ جدید را دریافت و دوباره تصمیم بگیرید.
- `429`: محدودیت تلاش ورود؛ `Retry-After` را رعایت کنید.

شیفت و پارت در این مرحله در همان روز آغاز و پایان می‌یابند. برنامهٔ شخصیِ پارت دانش‌آموز پیاده‌سازی نشده است؛ همهٔ دانش‌آموزان فعال سالن در همهٔ پارت‌های تخصیص‌یافتهٔ آن سالن هستند. داده‌های تاریخچه و snapshotها برای توسعهٔ گزارش‌ها حفظ می‌شوند.
