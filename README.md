# دماوند — مدیریت مرکزی و پرتال اختصاصی مجموعه‌ها

سامانهٔ مدیریت داخلی مجموعه‌ها با **Django 5.2، Django REST Framework، Next.js، TypeScript و Tailwind CSS**؛ رابط کاملاً فارسی و راست‌به‌چپ است و تاریخ‌ها را به تقویم هجری شمسی نمایش می‌دهد. Django مسئول احراز هویت، مجوزها، اعتبارسنجی و داده‌هاست؛ Next.js رابط مدیریت مرکزی و پرتال اختصاصی مجموعه‌ها را ارائه می‌کند. محیط توسعه روی ویندوز و PyCharm، بدون Docker، اجرا می‌شود.

فاز دوم، پرتال مستقل هر مجموعه را به پنل داخلی موجود اضافه می‌کند. مدیران مرکزی حساب اولیهٔ مجموعه را امن راه‌اندازی می‌کنند؛ هر مجموعه در نشانی خودش وارد می‌شود و تنها مشخصات، ظرفیت و اشتراک خودش را می‌بیند. انقضای اشتراک **صرفاً اطلاع‌رسانی** است و ورود یا داشبورد را مسدود نمی‌کند. فاز سوم، مدیریت سالن‌ها، پارت‌های مطالعاتی، تخصیص پارت‌ها و پروندهٔ دانش‌آموزان را اضافه می‌کند. فاز چهارم شامل پشتیبانی دوطرفه، اعلان‌های شخصی، مدیریت مراقبین و بهبود سایدبار و راهنمای زمینه‌ای است. حضور و غیاب، رزرو، پرداخت و حساب ورود دانش‌آموز یا مراقب هنوز پیاده‌سازی نشده‌اند.

## امکانات

- ورود و خروج با نام کاربری و رمز عبور، نشست Django و محافظت CSRF؛ مدیریت کاربران داخلی و نقش‌ها.
- ثبت، جست‌وجو، فیلتر، مرتب‌سازی، صفحه‌بندی و ویرایش مشتریان؛ اعتبارسنجی شمارهٔ همراه ایران.
- شناسهٔ دائمی، یکتا و غیرقابل‌تغییر برای هر مجموعه؛ تولید خودکار شناسه یا تعیین آن هنگام ثبت.
- تاریخ شروع و انقضا، تمدید خدمت، حذف نرم و بازیابی، و سابقهٔ فعالیت‌های مدیریتی.
- داشبورد مبتنی بر داده‌های واقعی، نمودارهای رشد و توزیع خدمات، هشدارهای انقضای ۷ و ۳۰ روزه، فیلتر تاریخ و خروجی CSV.
- رابط پاسخ‌گو، حالت‌های خالی، بارگذاری و خطا؛ تاریخ شمسی و نمایش اعداد فارسی با فونت Vazir FD.
- نشانی اختصاصی و ثابت هر مجموعه، ظرفیت مثبت و راه‌اندازی یا تغییر امن نام کاربری و رمز توسط مدیران؛ باز کردن و کپی نشانی در جزئیات مشتری.
- ورود سینمایی با هویت دماوند و داشبورد اختصاصی شامل مشخصات، ظرفیت، تقویم شمسی، پیشرفت و روزهای دقیق اشتراک؛ بدون آمار ساختگی.

- سالن‌های مستقل هر مجموعه با توضیحات، بایگانی و بازیابی امن؛ سالن دارای دانش‌آموز فعال بایگانی نمی‌شود.
- پارت‌های مطالعاتی مستقل از سالن، مرتب‌سازی همیشگی بر اساس ساعت و ماتریس چندبه‌چند تخصیص سطری و ستونی.
- پروندهٔ دانش‌آموز، جست‌وجو و فیلتر، صفحه‌بندی، انتقال گروهی و بایگانی/بازیابی؛ شناسهٔ یکتا در هر مجموعه و میز قابل تکرار.
- کنترل ظرفیت فعال در کل مجموعه، حفاظت در برابر ثبت هم‌زمان و داشبورد واقعی توزیع دانش‌آموزان و ظرفیت باقی‌مانده.
- تیکت متنی، گفت‌وگوی پایدار، ارجاع به پشتیبان مجاز، چرخهٔ حل/تأیید/بازگشایی و اعلان خوانده‌نشدهٔ جداگانه برای هر گیرنده.
- پروندهٔ مراقب با شمارهٔ همراه قابل تکرار، تخصیص چند سالن، فعال/غیرفعال‌کردن و بایگانی/بازیابی مستقل.
- سایدبار با اسکرول مستقل و خروج در دسترس، و راهنماهای کوتاه قابل استفاده با موس، صفحه‌کلید و لمس.

## پیش‌نیازها

- Git.
- Python **3.12 یا جدیدتر**؛ هنگام نصب ویندوز گزینهٔ افزودن Python به PATH را فعال کنید.
- Node.js **22.18 یا جدیدتر** و npm؛ این حداقل برای اجرای آزمون‌های TypeScript بدون ابزار اضافی هم مناسب است.
- PyCharm؛ قابلیت اختصاصی Django در نسخهٔ Professional اختیاری است. با تنظیم اجرای معمولی Python نیز می‌توانید سرور را اجرا کنید.

SQLite همراه Python نصب است و برای شروع به نصب سرور پایگاه داده نیاز نیست. پایگاه دادهٔ جدید فقط پس از اجرای migration ساخته می‌شود؛ دادهٔ نمایشی یا کاربر پیش‌فرض به‌صورت خودکار اضافه نمی‌شود.

```powershell

cd djangoverssion_pane_admin
```

پوشهٔ اصلی پروژه را در PyCharm باز کنید. ساختار اصلی:


## راه‌اندازی Django در ویندوز

از ریشهٔ پروژه:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
Copy-Item backend\.env.example backend\.env
cd backend
..\.venv\Scripts\python.exe manage.py migrate
..\.venv\Scripts\python.exe manage.py createsuperuser
..\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

اگر نسخهٔ دیگری از Python نصب کرده‌اید، فرمان ساخت محیط مجازی را با همان نسخهٔ سازگار اجرا کنید. اجرای مستقیم `python.exe` محیط مجازی نیاز به فعال‌سازی PowerShell ندارد؛ خطای Execution Policy را با تغییر سیاست سراسری ویندوز دور نزنید.

نام کاربری و رمز حساب خودتان را در `createsuperuser` انتخاب کنید. رمز باید حداقل ۱۰ نویسه داشته باشد و رمز رایج، کاملاً عددی یا بسیار شبیه اطلاعات کاربر نباشد. این حساب نقش مدیر کل دارد. هیچ رمز یا کاربر نمونه‌ای داخل کد قرار نگرفته است. ترمینال سرور را باز نگه دارید.

### تنظیمات backend/.env

فایل نمونه را برای توسعهٔ محلی کپی کنید؛ فایل `.env` در Git ثبت نمی‌شود. مقادیر حساس را در README یا فایل نمونه قرار ندهید.

| متغیر | کاربرد |
| --- | --- |
| `DEBUG` | برای توسعهٔ محلی `true`؛ در استقرار `false`. |
| `SECRET_KEY` | کلید تصادفی محرمانهٔ Django؛ با `DEBUG=false` الزامی است. |
| `ALLOWED_HOSTS` | نام میزبان‌های مجاز، با کاما جدا شوند؛ در توسعه `127.0.0.1,localhost`. |
| `CSRF_TRUSTED_ORIGINS` | مبداهای کامل مورد اعتماد، شامل پروتکل و پورت؛ در توسعه `http://127.0.0.1:3000,http://localhost:3000`. |
| `FRONTEND_URL` | نشانی کامل و عمومی رابط برای هدایت صفحهٔ اصلی Django؛ پیش‌فرض `http://127.0.0.1:3000/`. |
| `DATABASE_URL` | اختیاری؛ اگر خالی باشد SQLite محلی استفاده می‌شود. |
| `SESSION_COOKIE_SECURE` | ارسال کوکی نشست فقط روی HTTPS؛ پیش‌فرض در حالت production فعال است. |
| `CSRF_COOKIE_SECURE` | ارسال کوکی CSRF فقط روی HTTPS؛ پیش‌فرض در حالت production فعال است. |
| `SECURE_SSL_REDIRECT` | هدایت HTTP به HTTPS؛ پیش‌فرض در حالت production فعال است. |
| `SESSION_COOKIE_AGE` | طول عمر نشست به ثانیه؛ پیش‌فرض `28800`، معادل ۸ ساعت. |
| `TRUST_PROXY_HTTPS` | اعتماد به سرآیند HTTPS پروکسی؛ فقط در استقرار پشت پروکسی کنترل‌شده فعال شود. |

در حالت توسعه، اگر کلید تعیین نکرده باشید، کلید تصادفی محلی در `backend/.local-secret` نگه‌داری می‌شود. این فایل محرمانه است و مانند `.env` ثبت نمی‌شود؛ آن را به استقرار واقعی منتقل نکنید. برای تولید کلید خودتان:

```powershell
..\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(64))"
```

خروجی را فقط در تنظیمات خصوصی محیط قرار دهید. تغییر کلید می‌تواند نشست‌های موجود را نامعتبر کند.

کوکی نشست `HttpOnly` و `SameSite=Lax` است؛ نشست برای بسته‌شدن مرورگر هم تنظیم شده است. عمر ۸ ساعته، سقف زمانی پیش‌فرض است و به‌معنای قابلیت «مرا به خاطر بسپار» نیست.

## راه‌اندازی Next.js

یک ترمینال دیگر در ریشهٔ پروژه باز کنید:

```powershell
cd frontend
Copy-Item .env.example .env.local
npm ci
npm run dev
```

رابط را در **http://127.0.0.1:3000** باز کنید و با حساب ساخته‌شده وارد شوید. `npm run dev` برای Django محلی روی پورت ۸۰۰۰ ابتدا migrationها را با Python محیط `.venv` اجرا می‌کند، حتی اگر سرور Django از قبل روشن باشد؛ سپس API و کوکی CSRF را بررسی می‌کند. اگر Django فعال نباشد، سرور آن را نیز اجرا می‌کند و سپس Next.js را روشن می‌کند. اگر Django را از قبل اجرا کرده باشید، همان سرویس استفاده می‌شود. شکست migration مانع شروع Next.js می‌شود تا داشبورد با جدول‌های ناقص باز نشود. توقف این فرمان فقط سرویس‌هایی را متوقف می‌کند که خودش راه‌اندازی کرده است. برای `DJANGO_API_ORIGIN` غیرمحلی، backend باید جداگانه اجرا شده و migrationهای آن هم اعمال شده باشند.

صفحهٔ اصلی Django در `http://127.0.0.1:8000/` به نشانی `FRONTEND_URL` هدایت می‌شود. برای نمایش رابط، Next.js را نیز جداگانه با `npm run dev` اجرا کنید؛ اجرای Django به‌تنهایی رابط را راه‌اندازی نمی‌کند.

فایل `frontend/.env.local`:

```dotenv
DJANGO_API_ORIGIN=http://127.0.0.1:8000
```

این متغیر سمت سرور است. Next.js درخواست‌های `/api/` را به Django هدایت می‌کند تا مرورگر از یک مبدا به رابط و API دسترسی داشته باشد و نشست و CSRF درست کار کنند. بعد از تغییر این تنظیم، سرور Next.js را دوباره اجرا کنید. برای ورود و ادامهٔ کار از یک میزبان ثابت استفاده کنید؛ `localhost` و `127.0.0.1` کوکی‌های مشترک ندارند.

`DJANGO_API_ORIGIN` نشانی backend برای درخواست‌های Next.js است؛ `FRONTEND_URL` در تنظیمات Django، نشانی رابط برای مرورگر است. این دو متغیر مستقل‌اند و در توسعه به‌ترتیب پورت‌های ۸۰۰۰ و ۳۰۰۰ را دارند.

### تنظیم اجرای PyCharm

1. در تنظیمات **Python Interpreter** مسیر `.venv\Scripts\python.exe` در ریشهٔ پروژه را انتخاب کنید.
2. یک پیکربندی اجرای **Python** بسازید: فایل `backend\manage.py`، پارامترهای `runserver 127.0.0.1:8000` و Working directory برابر پوشهٔ `backend`.
3. برای رابط یک پیکربندی **npm** با `frontend\package.json` و اسکریپت `dev` بسازید، یا فرمان `npm run dev` را در ترمینال پوشهٔ `frontend` اجرا کنید.
4. فایل‌های `.env` و `.env.local` را مطابق نمونه‌ها بسازید؛ backend فایل `.env` خودش را می‌خواند و Next.js `.env.local` را بارگذاری می‌کند.
5. اگر گزینهٔ بازکردن مرورگر هنگام Run را فعال می‌کنید، نشانی آن را `http://127.0.0.1:3000/` قرار دهید. اجرای پیکربندی npm با اسکریپت `dev` برای راه‌اندازی هر دو سرویس محلی کافی است؛ Run پیکربندی Python به‌تنهایی رابط Next.js را اجرا نمی‌کند.

## نقش‌ها و دسترسی‌ها

مجوزها در API بررسی می‌شوند؛ پنهان‌شدن دکمه‌ها در رابط تنها بخش نمایشی است.

| قابلیت | اپراتور `operator` | مدیر `admin` | مدیر کل `super_admin` |
| --- | --- | --- | --- |
| مشاهدهٔ داشبورد و مشتریان، ثبت/ویرایش مشتری، تمدید | بله | بله | بله |
| حذف نرم و بازیابی مشتری | خیر | بله | بله |
| خروجی CSV و مشاهدهٔ سابقهٔ مدیریتی | خیر | بله | بله |
| مدیریت حساب‌های اپراتور | خیر | بله | بله |
| راه‌اندازی و تغییر اعتبارنامهٔ پرتال | خیر | بله | بله |
| مدیریت مدیران و مدیران کل و تعیین نقش‌های بالاتر | خیر | خیر | بله |
| مدیریت تیکت‌های همهٔ مجموعه‌ها | فقط با `can_support=true` | فقط با `can_support=true` | بله |
| اعطا یا لغو مجوز پشتیبانی `can_support` | خیر | خیر | بله |

مدیر نمی‌تواند خود را به مدیر کل ارتقا دهد یا حساب مدیر دیگری را از طریق API تغییر دهد. حذف یا غیرفعال‌کردن آخرین مدیر کل فعال مجاز نیست. رمز عبور با سازوکار Django نگه‌داری می‌شود و API آن را برنمی‌گرداند. حساب‌های مجموعه با نقش `tenant` به همان رکورد مشتری متصل‌اند و در فهرست کاربران داخلی نمایش داده نمی‌شوند.

مدیر می‌تواند فهرست کاربران را ببیند، اما عملیات مدیریت حساب فقط برای اپراتورها مجاز است. هر کاربر داخلی می‌تواند اطلاعات پروفایل و رمز خودش را تغییر دهد؛ تغییر رمز شخصی به رمز فعلی نیاز دارد. فعالیت‌های مدیریتی در داشبورد اپراتور نمایش داده نمی‌شوند.

مجوز پشتیبانی مستقل از نقش مدیریتی است: مدیر و اپراتور بدون اعطای صریح مجوز، به تیکت‌های مرکزی یا اعلان‌های آن‌ها دسترسی ندارند. فقط مدیر کل می‌تواند `can_support` را از بخش کاربران یا API تغییر دهد؛ تغییر پروفایل شخصی راهی برای گرفتن این مجوز نیست. ارجاع تیکت فقط به کاربر داخلی فعال و مجاز انجام می‌شود.

## قرارداد API

رابط از API واقعی Django استفاده می‌کند. در مرورگر مسیرها از همان مبدا Next.js ارسال می‌شوند؛ در توسعه می‌توان API را مستقیم روی پورت ۸۰۰۰ نیز بررسی کرد. پاسخ‌ها JSON هستند و برای عملیات نوشتن، علاوه بر کوکی نشست، CSRF معتبر لازم است.

| مسیر | کاربرد |
| --- | --- |
| `GET /api/auth/csrf/` | آماده‌سازی کوکی CSRF پیش از ورود یا عملیات نوشتن. |
| `POST /api/auth/login/` و `POST /api/auth/logout/` | ورود و خروج نشست. |
| `GET/PATCH /api/auth/me/` | دریافت کاربر فعلی یا تغییر اطلاعات پروفایل. |
| `POST /api/auth/password/` | تغییر رمز شخصی با رمز فعلی و رمز جدید. |
| `/api/customers/` و `/api/customers/{id}/` | فهرست/ثبت و جزئیات/ویرایش/حذف نرم مشتریان. |
| `POST /api/customers/{id}/renew/` و `POST /api/customers/{id}/restore/` | تمدید و بازیابی. |
| `GET /api/customers/export/` | خروجی CSV با همان فیلترهای فهرست و مجوز مدیر. |
| `/api/users/` و `POST /api/users/{id}/reset_password/` | مدیریت کاربران و بازنشانی مجاز رمز. |
| `GET /api/dashboard/` و `GET /api/audit/` | آمار واقعی و سابقهٔ مدیریتی. |

فهرست مشتریان پارامترهای `search`، `status`، `deleted`، `ordering`، `page` و `page_size` دارد. وضعیت‌ها `scheduled`، `active`، `expiring` و `expired` هستند؛ فیلتر `status=current` سرویس‌های فعال و نزدیک انقضا را با هم برمی‌گرداند. فیلتر حذف یکی از `active`، `deleted` یا `all` است. بازهٔ تاریخ با `start_date_from/to`، `expiration_date_from/to` و `created_date_from/to` و تاریخ میلادی `YYYY-MM-DD` ارسال می‌شود. بازهٔ `date_from/date_to` داشبورد بر **تاریخ ایجاد رکورد مشتری** اعمال می‌شود و در لینک آمار به فهرست مشتریان حفظ می‌شود. رابط تبدیل شمسی/میلادی را انجام می‌دهد.

## قواعد داده و تاریخ

نام مجموعه، نام مدیر، شمارهٔ همراه، شناسهٔ یکتا، تاریخ شروع و تاریخ انقضا اطلاعات اصلی مشتری هستند. شمارهٔ همراه ایران به فرم `09xxxxxxxxx` ذخیره می‌شود؛ ورودی با ارقام فارسی/عربی و پیش‌شمارهٔ `+98` نیز نرمال می‌شود. شماره‌ها و شناسه‌ها با جهت مناسب نمایش داده می‌شوند تا ترتیب نویسه‌ها در محیط RTL عوض نشود.

شناسهٔ مشتری شامل ۴ تا ۳۲ حرف یا رقم ASCII است؛ گزینهٔ تولید خودکار نیز موجود است. این شناسه پس از ایجاد تغییر نمی‌کند؛ حذف نرم و بازیابی هم آن را حفظ می‌کنند. شناسه برای اتصال آینده به نرم‌افزار اصلی طراحی شده و عمومی محسوب می‌شود. آن را به‌عنوان API key، رمز عبور یا اثبات هویت استفاده نکنید.

تاریخ‌ها در پایگاه داده و API با قالب استاندارد میلادی نگه‌داری می‌شوند؛ انتخاب‌گر تقویم و نمایش رابط شمسی هستند. محاسبهٔ روز جاری و وضعیت خدمت بر اساس **Asia/Tehran** است. چهار وضعیت خودکار:

- «زمان‌بندی‌شده»: تاریخ شروع هنوز نرسیده است.
- «منقضی»: تاریخ پایان قبل از امروز است.
- «در آستانهٔ انقضا»: خدمت شروع شده و بین صفر تا ۳۰ روز، شامل دو انتهای بازه، تا انقضا باقی مانده است.
- «فعال»: خدمت شروع شده و بیش از ۳۰ روز تا انقضا باقی مانده است.

شاخص «خدمات فعال» داشبورد، خدمات فعال و در آستانهٔ انقضا را با هم می‌شمارد. گزارش هشدار، بازهٔ ۷ روزه را هم دارد. تمدید، تاریخ انقضا را با اعتبارسنجی سمت سرور تغییر می‌دهد و در سابقه ثبت می‌شود.

حذف مشتری به‌صورت نرم انجام می‌شود؛ رکورد و شناسه برای بازیابی و بررسی سابقه حفظ می‌شوند. انقضا ورود پرتال را مسدود نمی‌کند. حذف نرم، پرتال همان مجموعه را از دسترس خارج و نشست‌های موجود آن را لغو می‌کند؛ بازیابی اجازهٔ ورود مجدد می‌دهد.

## پرتال اختصاصی و نمونهٔ آفتاب

۱. هر دو سرویس را اجرا کنید و با حساب داخلی مدیر یا مدیر کل در `http://127.0.0.1:3000/login` وارد شوید.
۲. از «مشتریان ← مجموعه جدید»، نام «مجموعه آفتاب»، مدیر، شماره تماس، ظرفیت واقعی مثبت و تاریخ‌های شروع و پایان را وارد کنید. برای مثال آزمایشی ظرفیت ۱۲۰ را انتخاب کنید. «نشانی اختصاصی پرتال» را **aftab** بگذارید؛ شناسهٔ اتصال قدیمی مستقل است و می‌تواند خودکار تولید شود.
۳. «هم‌زمان ورود اختصاصی مجموعه را راه‌اندازی کن» را فعال کنید. نام کاربری مثلاً **aftab.manager** و رمز قوی انتخابی خودتان را وارد کنید. هیچ رمز نمونهٔ ثابت یا اعتبارنامهٔ پیش‌فرض وجود ندارد.
۴. پس از ثبت، صفحهٔ جزئیات مجموعه بخش «پرتال اختصاصی مجموعه» را نشان می‌دهد. نشانی را کپی کنید یا «باز کردن ورود مجموعه» را بزنید.
۵. ورود اختصاصی در `http://127.0.0.1:3000/aftab` و داشبورد پس از ورود در `http://127.0.0.1:3000/aftab/dashboard` است. برای آزمون جداسازی، مجموعهٔ دوم با نشانی متفاوت بسازید؛ تغییر نشانی داشبورد به مجموعهٔ دوم باید رد شود.

در جزئیات مشتری، «تنظیم دسترسی پرتال» نام کاربری، رمز جدید، ظرفیت و فعال‌بودن حساب را تنظیم می‌کند. خالی‌گذاشتن رمز جدید، رمز قبلی را حفظ می‌کند. هر تنظیم دسترسی، نشست‌های قبلی حساب را لغو می‌کند. تغییر ظرفیت یا جزئیات مشتری و تمدید سرویس بدون تکرار رکورد در داشبورد منعکس می‌شوند؛ دکمهٔ به‌روزرسانی اطلاعات، آخرین وضعیت را دریافت می‌کند.

### مهاجرت ایمن داده‌های قبلی

پیش از به‌روزرسانی، از پایگاه داده نسخهٔ پشتیبان بگیرید و `manage.py migrate` را اجرا کنید. migration شمارهٔ **0003_organization_portal** برای هر مشتری قدیمی نشانی یکتای `org-<identifier>` ایجاد می‌کند و تعارض حروف بزرگ/کوچک را رفع می‌کند. شناسهٔ اتصال و اطلاعات قدیمی حفظ می‌شوند. ظرفیت قدیمی `NULL` یعنی نامشخص است؛ هیچ ظرفیت، رمز یا حسابی حدس زده نمی‌شود. مدیر باید ظرفیت واقعی و اعتبارنامه را در بخش تنظیم پرتال ثبت کند تا صفحهٔ ورود فعال شود. نشانی و شناسه پس از ایجاد تغییرپذیر نیستند؛ نشانی‌های سیستمی مثل `login`، `dashboard`، `api` و `customers` رزرو شده‌اند. نشانی ناشناخته یا پرتال راه‌اندازی‌نشده صفحهٔ ۴۰۴ دارد.

### جداسازی هویت و اشتراک

همان مدل Django `User` استفاده می‌شود. حساب‌های مجموعه از طریق `organization` به `Customer` متصل‌اند؛ نام کاربری نمایشی در هر مجموعه یکتاست و مدل برای چند حساب کارکنان در آینده آماده است. اعتبارنامه‌ها با هش استاندارد Django ذخیره می‌شوند؛ رمز و هش و نام کاربری داخلی ذخیره‌سازی در API برگردانده نمی‌شوند. فقط مدیران داخلی مجاز می‌توانند نام کاربری پرتال را ببینند یا تنظیم کنند.

دو backend احراز هویت و دو کوکی مستقل وجود دارند: نشست مرکزی `sessionid` و نشست مجموعه `damavand_portal_session` با مسیر `/api/organizations/`. ورود و خروج یکی نشست دیگری را تغییر نمی‌دهد. نسخهٔ اعتبارنامه در هش نشست لحاظ می‌شود تا تغییر نام کاربری، رمز، وضعیت حساب یا حذف نرم، نشست قدیمی را باطل کند. API خصوصی سازمان از هویت نشست و مالکیت backend استفاده می‌کند؛ slug یا پارامتر شناسهٔ ارسالی اثبات مجوز نیست. همهٔ APIهای مرکزی کاربران tenant را رد می‌کنند. CSRF برای ورود و عملیات نوشتن، HttpOnly و SameSite برای نشست و محدودسازی پایدار حساب/IP برقرارند؛ HTTPS تولیدی کوکی Secure لازم دارد. به‌دلیل چرخش کوکی مشترک CSRF، رابط پیش از هر عملیات نوشتن توکن تازه می‌گیرد.

API پرتال:

| مسیر | رفتار |
| --- | --- |
| `GET /api/organizations/<slug>/public/` | فقط نام و نشانی مجموعه، بدون مشخصات خصوصی یا اعتبارنامه |
| `POST /api/organizations/<slug>/login/` | ورود واقعی، CSRF و محدودسازی تلاش |
| `GET /api/organizations/<slug>/dashboard/` | مشخصات و اشتراک فقط برای عضو همان مجموعه |
| `POST /api/organizations/<slug>/logout/` | خروج از نشست پرتال، CSRF و کنترل مالکیت |
| `POST /api/customers/<id>/portal/` | تنظیم دسترسی توسط مدیر مرکزی مجاز |

روز پایان **شامل سرویس است**: در همان روز یک روز باقی می‌ماند؛ روز بعد مقدار صفر و وضعیت منقضی است. پیش از شروع، مدت کامل دوره و روزهای تا آغاز جداگانه نمایش داده می‌شوند. بازهٔ هشدار بر اساس فاصلهٔ تاریخ پایان تا امروز حداکثر ۳۰ روز است؛ با احتساب امروز ممکن است ۳۱ روز خدمت باقی باشد. پیشرفت، روزهای کامل گذشته از دوره را نشان می‌دهد و پس از پایان به ۱۰۰٪ می‌رسد. API قدیمی `days_remaining` برای سازگاری فاصلهٔ تاریخی قبلی را حفظ می‌کند؛ اطلاعات دقیق و شامل روز پایان در `subscription.remaining_days` است. همهٔ محاسبات تاریخ تجاری با Asia/Tehran انجام می‌شوند.

راهنمای مستقل اجرای هر دو محیط در [PYCHARM_SETUP.md](PYCHARM_SETUP.md) قرار دارد.

## فاز سوم — عملیات سالن مطالعه

از همان شاخهٔ `feature/admin-panel-v1` استفاده کنید. قبل از migration از پایگاه دادهٔ موجود نسخهٔ پشتیبان بگیرید؛ نیازی به پاک‌کردن پایگاه داده، ساخت حساب جدید برای مجموعه‌های موجود یا اجرای seed نیست. migration جدید `operations/0001_initial` چهار جدول مستقل اضافه می‌کند و مشتریان، کاربران، رمزها و اشتراک‌های قبلی را تغییر نمی‌دهد.

```powershell
git checkout feature/admin-panel-v1
git pull --ff-only origin feature/admin-panel-v1
.\.venv\Scripts\python.exe -m pip install -r backend\requirements-dev.txt
cd backend
..\.venv\Scripts\python.exe manage.py migrate
..\.venv\Scripts\python.exe manage.py check
cd ..\frontend
npm ci
npm run dev
```

فایل‌های خصوصی `.env` و `.env.local` موجود را حفظ کنید. `npm run dev`، Django محلی و Next.js را با یک فرمان اجرا می‌کند؛ اگر backend از قبل سالم باشد، همان پردازه استفاده می‌شود. `npm start` برای نسخهٔ buildشده است و backend را خودکار اجرا نمی‌کند. دستورهای Python این راهنما در لینوکس با `.venv/bin/python` اجرا می‌شوند.

### گردش کار مجموعه

برای مجموعه‌ای با slug برابر `aftab`، در `/aftab` وارد شوید. چهار گزینهٔ جدید در سایدبار قرار دارد:

| نشانی | کاربرد |
| --- | --- |
| `/aftab/halls` | ساخت/ویرایش سالن، توضیحات، مشاهدهٔ تعداد دانش‌آموز فعال، بایگانی/بازیابی |
| `/aftab/study-sessions` | ساخت/ویرایش پارت با ساعت شروع و پایان؛ همواره به ترتیب زمانی |
| `/aftab/assignments` | ماتریس سالن × پارت؛ انتخاب خانه، تمام سطر، ستون یا کل جدول و ذخیرهٔ یکپارچه |
| `/aftab/students` | ثبت، جست‌وجو، فیلتر، مرتب‌سازی، صفحه‌بندی و عملیات گروهی |
| `/aftab/students/<id>` | پرونده، ویرایش، بایگانی و بازیابی دانش‌آموز |

۱. یک یا چند سالن بسازید. هیچ ظرفیت اجباری یا محدودیت ساختگی برای هر سالن وجود ندارد.
۲. پارت‌ها را با ساعت‌های همان روز بسازید. پایان باید **بزرگ‌تر از شروع** باشد؛ ساعت برابر یا بازهٔ شبانه رد می‌شود. پارت به مجموعه تعلق دارد و می‌تواند در چند سالن استفاده شود. نمایش فهرست، صفحه‌بندی API و ستون‌های ماتریس همیشه بر اساس ساعت شروع است.
۳. در ماتریس، پارت‌ها را به سالن‌ها تخصیص دهید و «ذخیره تخصیص‌ها» را بزنید. عملیات ذخیره، کل ماتریس فعال همان مجموعه را به‌صورت تراکنشی جایگزین می‌کند؛ خانهٔ خالی یعنی برداشتن تخصیص. هیچ داده‌ای از مجموعهٔ دیگر پذیرفته نمی‌شود. در ویرایش هم‌زمان ماتریس، آخرین ذخیره معتبر می‌ماند.
۴. دانش‌آموز را با شناسه، نام، نام خانوادگی، همراه اصلی، پایه، رشته و سالن فعال ثبت کنید. همراه دوم و شمارهٔ میز اختیاری‌اند. همراه ایران با ارقام فارسی/عربی/انگلیسی و قالب‌های `09…`، `+98…` و `0098…` پذیرفته و به قالب `09…` ذخیره می‌شود.
۵. پایه‌ها: هفتم تا دوازدهم و فارغ‌التحصیل؛ رشته‌ها: علوم انسانی، ریاضی و فیزیک، علوم تجربی و سایر. شمارهٔ میز تکراری مجاز است. شناسه در هر مجموعه یکتا است؛ مجموعه‌های مختلف می‌توانند شناسهٔ یکسان داشته باشند. شناسهٔ پروندهٔ بایگانی‌شده نیز محفوظ می‌ماند.
۶. برای انتقال گروهی، ردیف‌های صفحه را انتخاب کنید و سالن مقصد را تعیین کنید. بایگانی و بازیابی گروهی هم وجود دارد. هر درخواست گروهی حداکثر ۲۰۰ شناسه می‌پذیرد و همهٔ موارد با هم انجام می‌شوند یا هیچ‌کدام انجام نمی‌شوند.

### ظرفیت و بایگانی

ظرفیت پنل مرکزی، سقف **مجموع دانش‌آموزان فعال در همهٔ سالن‌ها** است. پروندهٔ بایگانی‌شده ظرفیت مصرف نمی‌کند؛ ویرایش و انتقال دانش‌آموز فعال نیز ثبت‌نام تازه محسوب نمی‌شود. بازیابی پرونده ظرفیت می‌خواهد و سالن مقصد باید فعال باشد.

ثبت، بازیابی، انتقال، بایگانی سالن و تخصیص‌ها همگی در تراکنش با قفل رکورد مشتری انجام می‌شوند. PostgreSQL از `SELECT FOR UPDATE` و SQLite از تنظیم موجود `transaction_mode=IMMEDIATE` استفاده می‌کند؛ شمارندهٔ حافظه‌ای وجود ندارد. `Student.save()` عادی نیز کنترل ظرفیت و مالکیت سالن را اجرا می‌کند. برای ایجاد یا فعال‌سازی دانش‌آموز از `bulk_create`، `QuerySet.update` یا SQL مستقیم استفاده نکنید؛ این مسیرها قواعد مدل و ظرفیت را اجرا نمی‌کنند. عملیات گروهی API از مسیر اعتبارسنجی و ذخیرهٔ هر دانش‌آموز در یک تراکنش عبور می‌کند.

اگر مدیریت مرکزی ظرفیت را پایین‌تر از تعداد فعلی ببرد، هیچ دانش‌آموزی حذف نمی‌شود. هشدار در داشبورد و فهرست دانش‌آموزان دیده می‌شود؛ ویرایش و انتقال برقرار است و ثبت/بازیابی جدید تا پایین‌آمدن تعداد فعال از سقف ظرفیت رد می‌شود. کاهش ظرفیت در همان قفل مشترک مدیریت مرکزی انجام می‌شود.

سالن دارای دانش‌آموز فعال بایگانی نمی‌شود؛ ابتدا آن‌ها را منتقل یا بایگانی کنید. بایگانی سالن یا پارت، تخصیص‌های مربوط را پاک می‌کند. بازیابی آن‌ها تخصیص‌های قدیمی را خودکار بازنمی‌گرداند. پروندهٔ دانش‌آموز بایگانی‌شده و ارجاع سالن آن محفوظ می‌ماند؛ می‌توانید پیش از بازیابی، سالن فعال دیگری انتخاب کنید.

داشبورد تعداد ثبت‌نام فعال، ظرفیت کل و باقی‌مانده، درصد استفاده، تعداد سالن و پارت فعال و توزیع دانش‌آموزان را از پایگاه داده می‌خواند. درصد بالای ۱۰۰٪ پس از کاهش ظرفیت به‌درستی نمایش داده می‌شود. این آمار **حضور فیزیکی یا اشغال لحظه‌ای میز نیست**. انقضای اشتراک همچنان فقط هشدار است.

| `students/` و `students/<id>/` | CRUD؛ DELETE نرم، شناسهٔ یکتای سازمانی در قید پایگاه داده |
| `<resource>/<id>/restore/` | POST برای بازیابی سالن، پارت یا دانش‌آموز |
| `students/bulk/` | POST با `ids` و `action` برابر `archive`، `restore` یا `transfer`؛ برای انتقال `hall` نیز لازم است |
| `assignments/` | GET ماتریس؛ PUT با `{"assignments":[{"hall":1,"session":2}]}`؛ فهرست خالی یعنی پاک‌کردن تخصیص‌های مجموعه |
| `dashboard/` | اطلاعات قبلی و بخش جدید `operations` شامل آمار واقعی |

فهرست‌ها از `status=active|archived|all`، `search`، `page` و `page_size` تا ۱۰۰ پشتیبانی می‌کنند. دانش‌آموزان علاوه بر آن `hall`، `grade`، `major` و `ordering` دارند؛ مرتب‌سازی مجاز بر اساس شناسه، نام، نام خانوادگی، میز، پایه و زمان ثبت/ویرایش با پیشوند اختیاری `-` است. حالت پیش‌فرض فعال‌هاست. سقف تعداد سالن یا پارت در مدل و API تعریف نشده است.

آزمون‌های `manage.py test`، CRUD، مالکیت، CSRF، یکتایی، بایگانی/بازیابی، انتقال، عملیات گروهی تراکنشی، ترتیب زمانی و حفظ داده‌های پیش از migration را پوشش می‌دهند. آزمون رقابت از دو پردازهٔ واقعی و SQLite فایل‌محور موقت استفاده می‌کند و رقابت ثبت/ثبت و ثبت/بازیابی برای آخرین ظرفیت را بررسی می‌کند؛ به پایگاه دادهٔ توسعه دست نمی‌زند. این اجرا جای آزمون عملی PostgreSQL را نمی‌گیرد.

آزمون مرورگر `e2e/run.py` علاوه بر گردش‌های قبلی، فرم‌ها، ماتریس، ظرفیت، انتقال، بایگانی/بازیابی، جست‌وجو/فیلتر/صفحه‌بندی و اندازهٔ موبایل را بررسی می‌کند. برای تست راه‌انداز توسعه از `e2e/run.py --dev` استفاده کنید. تصاویر عملیات در `e2e/artifacts/operations-*.png` ذخیره می‌شوند و در Git قرار نمی‌گیرند.

## فاز چهارم — پشتیبانی، مراقبین و راهنمای زمینه‌ای

برای به‌روزرسانی همان شاخه، از ریشهٔ پروژه در PowerShell اجرا کنید؛ پیش از migration از پایگاه دادهٔ موجود نسخهٔ پشتیبان بگیرید و تنظیمات خصوصی را حفظ کنید:

```powershell
git pull --ff-only origin feature/admin-panel-v1
.\.venv\Scripts\python.exe -m pip install -r backend\requirements-dev.txt
.\.venv\Scripts\python.exe backend\manage.py migrate --noinput
.\.venv\Scripts\python.exe backend\manage.py check
cd frontend
npm ci
npm run dev
```

migrationها جدول‌های تیکت، پیام، تاریخچهٔ وضعیت، اعلان و مراقب/تخصیص سالن را اضافه می‌کنند؛ پرونده‌ها و اعتبارنامه‌های قبلی حفظ می‌شوند. هیچ حساب مراقب، رمز یا دادهٔ نمونه‌ای خودکار ساخته نمی‌شود. راه‌انداز `npm run dev` migrationهای Django محلی را حتی وقتی آن سرور روشن است اجرا می‌کند؛ خطای migration باید پیش از بازکردن داشبورد برطرف شود.

### تیکت و گفت‌وگو

در پرتال مجموعه، **پشتیبانی و تیکت‌ها** را باز کنید (`/aftab/support`). موضوع، دسته‌بندی، اولویت و شرح الزامی‌اند. فهرست فقط تیکت‌های همان مجموعه را نشان می‌دهد؛ جزئیات در `/aftab/support/<id>` شامل گفت‌وگو و سابقهٔ وضعیت است. پیام‌ها متنی‌اند؛ فایل، ایمیل، پیامک یا اعلان بیرون از سامانه در این فاز وجود ندارد.

در پنل مرکزی، **مدیریت تیکت‌ها** (`/support`) برای مدیر کل و کاربران دارای مجوز صریح پشتیبانی نمایش داده می‌شود. جست‌وجو و فیلتر مجموعه، وضعیت، اولویت و بازهٔ تاریخ روی دادهٔ واقعی اعمال می‌شوند. تیکت را می‌توان به پشتیبان فعال و مجاز ارجاع داد و پاسخ یا نتیجهٔ رسیدگی را ثبت کرد.

| رویداد | وضعیت حاصل |
| --- | --- |
| ثبت تیکت توسط مجموعه | `open` — باز |
| پاسخ مجموعه در تیکت فعال | `awaiting_support` — منتظر پشتیبانی |
| پاسخ پشتیبان در تیکت فعال | `awaiting_customer` — منتظر مجموعه |
| اعلام حل‌شدن توسط پشتیبان | `resolved` — حل‌شده |
| تأیید حل‌شدن توسط مجموعه | `closed` — بسته |
| بازگشایی تیکت حل‌شده یا بسته توسط مجموعه | `awaiting_support` — منتظر پشتیبانی |

برای ادامهٔ گفت‌وگو در تیکت حل‌شده یا بسته، مجموعه ابتدا «بازگشایی» را انجام می‌دهد؛ ارسال مستقیم پاسخ در این دو وضعیت رد می‌شود. بستن فقط پس از حل‌شدن مجاز است. پیام‌ها و تغییر وضعیت با زمان و عامل تغییر ثبت می‌شوند؛ کاربر امکان دست‌کاری یا حذف پیام‌های ثبت‌شده را ندارد. متن به‌عنوان متن عادی نمایش داده می‌شود و HTML کاربر اجرا نمی‌شود.

زنگ اعلان، پیام‌ها و تغییر وضعیت را با polling دوره‌ای و بدون نیاز به بازخوانی صفحه دریافت می‌کند. وضعیت خوانده‌شدن **برای هر گیرنده جداست**؛ خواندن توسط یک پشتیبان، اعلان پشتیبان دیگر را پاک نمی‌کند. دریافت هر صفحهٔ گفت‌وگو فقط پیام‌های همان صفحه را برای کاربر جاری خوانده‌شده می‌کند؛ پیام‌های صفحه‌های بازنشده خوانده‌نشده می‌مانند. اعلان‌های وضعیت و ارجاع نیز جداگانه یا همراه اعلان‌های نمایش‌داده‌شده قابل علامت‌گذاری‌اند. فهرست زنگ حداکثر ۲۰ اعلان را با اولویت خوانده‌نشده‌ها نشان می‌دهد تا خواندن اعلان‌های تازه، اعلان‌های قدیمی‌تر را در دسترس قرار دهد. شمارندهٔ پیام خوانده‌نشده با شمارندهٔ کل اعلان‌ها متفاوت است؛ اعلان ارجاع یا وضعیت، پیام گفت‌وگو محسوب نمی‌شود. اطلاعات پشتیبانی داشبورد از همین داده‌های پایدار محاسبه می‌شود.

### API پشتیبانی

پیشوند مرکزی `/api/support/` و پیشوند مجموعه `/api/organizations/<slug>/support/` است. نشست و CSRF موجود استفاده می‌شوند؛ API مجموعه فقط مالک همان مجموعه و API مرکزی فقط پشتیبان مجاز را می‌پذیرد.

| مسیر زیر پیشوند | قرارداد |
| --- | --- |
| `tickets/` | GET فهرست صفحه‌بندی‌شده؛ POST فقط مجموعه با `subject,category,priority,description` |
| `tickets/<id>/` | GET جزئیات و ۵۰ تغییر وضعیت آخر به ترتیب زمانی در `status_history`؛ `status_history_count` تعداد کامل تغییرهاست |
| `tickets/<id>/history/` | GET تمام سابقهٔ وضعیت با صفحه‌بندی، تازه‌ترین تغییرها در صفحهٔ اول |
| `tickets/<id>/messages/` | GET گفت‌وگو با صفحه‌بندی؛ ترتیب پیش‌فرض زمانی و `ordering=-created_at` برای دریافت صفحهٔ تازه‌ترین پیام‌ها؛ POST با `body` |
| `tickets/<id>/transition/` | POST با `action=resolve` برای پشتیبان؛ `close` یا `reopen` برای مجموعه |
| `tickets/<id>/assign/` | POST مرکزی با `assigned_to` شناسهٔ پشتیبان مجاز یا `null` |
| `notifications/` | GET شمارنده‌ها و حداکثر ۲۰ اعلان همان گیرنده، خوانده‌نشده‌ها در اولویت |
| `notifications/read/` | POST با `ids` یا `ticket_id`؛ فقط اعلان‌های گیرندهٔ جاری؛ همراه `ticket_id`، مقدار `include_messages=false` فقط اعلان وضعیت/ارجاع را می‌خواند |
| `staff/` | GET مرکزی، فهرست پشتیبان‌های فعال و مجاز |

دسته‌بندی‌های API `general,technical,billing,account` و اولویت‌ها `low,normal,high,urgent` هستند. فهرست تیکت‌ها `search,status,priority,organization,date_from,date_to,page` را می‌پذیرد؛ فیلتر مجموعه فقط در پنل مرکزی معنا دارد. `unread=true|false` بر اساس پیام‌های خوانده‌نشدهٔ گیرندهٔ جاری و `unanswered=true|false` بر اساس وضعیت باز یا منتظر پشتیبانی فیلتر می‌کنند؛ ورودی نامعتبر رد می‌شود. تاریخ فیلتر API میلادی است و رابط انتخاب و نمایش شمسی را انجام می‌دهد. رابط تازه‌ترین صفحهٔ پیام‌ها را دریافت و حباب‌های آن را به ترتیب زمانی نمایش می‌دهد؛ صفحه‌بندی برای خواندن پیام‌های پیشین در دسترس است.

### مراقبین و تخصیص سالن

در پرتال **مدیریت مراقبین** (`/aftab/supervisors`) را باز کنید. نام، نام خانوادگی و همراه ایران الزامی‌اند؛ ارقام فارسی/عربی و قالب‌های بین‌المللی معتبر مانند `+98` به قالب `09…` نرمال می‌شوند. شمارهٔ همراه در یک مجموعه یا مجموعه‌های مختلف **می‌تواند تکراری باشد** و شناسهٔ حساب ورود نیست.

هر مراقب دقیقاً به یک مجموعه تعلق دارد و رابطهٔ چندبه‌چند با سالن‌های همان مجموعه دارد. می‌توان بدون سالن یا با چند سالن پرونده ساخت و بعداً تخصیص را تغییر داد. انتخاب‌گر قابل جست‌وجو، سالن‌های فعال همان مجموعه را عرضه می‌کند؛ شناسهٔ سالن مجموعهٔ دیگر در API و لایهٔ رابطه رد می‌شود. فهرست و جزئیات، سالن‌های تخصیص‌یافته را نشان می‌دهند.

غیرفعال‌کردن، پرونده و تخصیص‌های مراقب را حفظ می‌کند. بایگانی، پرونده را از فهرست پیش‌فرض کنار می‌گذارد و وضعیت فعال/غیرفعال و تخصیص‌ها را نگه می‌دارد؛ بازیابی همان وضعیت پیشین را برمی‌گرداند. برای ویرایش یا فعال‌کردن پروندهٔ بایگانی‌شده ابتدا آن را بازیابی کنید. شاخص مراقبین فعال، پرونده‌های بایگانی‌شده یا غیرفعال را نمی‌شمارد. حساب ورود مراقب، رمز، حضور و غیاب، ورود/خروج دانش‌آموز و گزارش عملیاتی هنوز ساخته نمی‌شوند.

API زیر `/api/organizations/<slug>/supervisors/` قرار دارد: GET/POST فهرست، GET/PATCH جزئیات و POST عملیات `archive/`، `restore/`، `activate/` و `deactivate/` روی `<id>/`. DELETE نیز بایگانی نرم است و JSON پرونده را برمی‌گرداند. فیلدهای قابل نوشتن `first_name,last_name,phone,is_active,halls` هستند؛ `halls` فهرست شناسه‌هاست و `hall_details` اطلاعات نمایشی سالن‌ها را برمی‌گرداند. ارسال `halls` تخصیص سالن‌های فعال را جایگزین می‌کند و ارتباط با سالن‌های قبلاً بایگانی‌شده را حفظ می‌کند. فهرست صفحه‌بندی‌شده، `status=active|inactive|archived|all` (پیش‌فرض فعال)، `hall`، `search` و `ordering` بر اساس نام، نام خانوادگی یا زمان ثبت/ویرایش با پیشوند اختیاری `-` را می‌پذیرد.

### رابط و کنترل‌های کیفیت

ناوبری سایدبار مستقل از صفحه اسکرول می‌شود و خروج در پایین در دسترس می‌ماند. در موبایل، منو با دکمه باز می‌شود، فوکوس در منو می‌ماند و Escape آن را می‌بندد. دکمهٔ `?` کنار بخش‌های مرتبط، راهنمای کوتاه فارسی را با hover یا فوکوس صفحه‌کلید و در موبایل با لمس نشان می‌دهد؛ Escape، خروج فوکوس یا لمس بیرون آن را می‌بندد. هشدار ظرفیت، اعتبارسنجی و اطلاعات ضروری همچنان در خود صفحه دیده می‌شوند.

کنترل‌های بخش بعد شامل آزمون‌های مجوز پشتیبانی، جداسازی مجموعه‌ها، چرخهٔ تیکت و اعلان هر گیرنده و CRUD/تخصیص/بایگانی مراقبین‌اند. گردش مرورگر فاز چهارم در `e2e/phase4_workflows.py` همراه اجرای `e2e/run.py` روی پایگاه دادهٔ موقت اجرا می‌شود؛ گفت‌وگوی واقعی دوطرفه، اعلان، تخصیص چند سالن، شمارهٔ تکراری، راهنما و منوی موبایل را بررسی می‌کند.

## دادهٔ نمایشی اختیاری

برای دیدن نمودارها و جدول‌ها با دادهٔ فارسی، پس از migration در پوشهٔ `backend`:

```powershell
..\.venv\Scripts\python.exe manage.py seed_demo --customers 24
```

این فرمان فقط مشتریان نمونه ایجاد می‌کند و حساب کاربری یا رمز پیش‌فرض نمی‌سازد. اجرا اختیاری است؛ پایگاه دادهٔ تازه بدون مشتری نیز باید حالت‌های خالی مناسب را نمایش دهد.

## اجرای کنترل‌های کیفیت

آزمون‌های Django پایگاه دادهٔ آزمون جداگانه می‌سازند و نیازی به seed ندارند:

```powershell
cd backend
..\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
..\.venv\Scripts\python.exe manage.py check
..\.venv\Scripts\python.exe manage.py test
..\.venv\Scripts\python.exe -m ruff check .
..\.venv\Scripts\python.exe -m ruff format --check .
```

در ترمینال رابط:

```powershell
cd frontend
npm run lint
npm run format:check
npm run typecheck
npm test
npm run build
```

بعد از build، اجرای `npm start` نسخهٔ ساخته‌شدهٔ Next.js را روی همان پورت پیش‌فرض ۳۰۰۰ راه‌اندازی می‌کند. `runserver` برای توسعه است و برای استقرار واقعی جایگزین سرور WSGI/ASGI نیست.

### آزمون یکپارچه با مرورگر

از ریشهٔ پروژه، پس از `npm run build` در پوشهٔ رابط:

```powershell
.\.venv\Scripts\python.exe -m pip install -r e2e\requirements.txt
.\.venv\Scripts\python.exe -m playwright install chromium
.\.venv\Scripts\python.exe e2e\run.py
```

پیش از اجرا، سرورهای دستی روی پورت‌های ۸۰۰۰ و ۳۰۰۰ را متوقف کنید. build رابط برای این آزمون باید با `DJANGO_API_ORIGIN=http://127.0.0.1:8000` ساخته شده باشد. این اجراکننده هر دو سرویس را برای آزمون روشن می‌کند و از پایگاه داده و کاربران موقت خودش استفاده می‌کند؛ دادهٔ توسعه نباید با دادهٔ آزمون جایگزین شود. خروجی‌ها و تصویرهای آزمون در `e2e/artifacts/` تولید می‌شوند و ثبت نمی‌شوند. برای اجرای headless به نصب مرورگر Playwright نیاز است؛ در لینوکس ممکن است کتابخانه‌های سیستمی مرورگر نیز لازم باشند.

برای اجرای همین آزمون‌ها روی راه‌انداز یکپارچهٔ توسعه، از ریشهٔ پروژه فرمان `.\.venv\Scripts\python.exe e2e\run.py --dev` را اجرا کنید. این حالت به build نیاز ندارد؛ آماده‌شدن Django و Next.js از طریق `npm run dev`، خطای موقت CSRF و ورود موفق پس از بازیابی سرویس را نیز بررسی می‌کند.

## PostgreSQL و استقرار

برای استفاده از PostgreSQL، پایگاه داده و کاربر اختصاصی با دسترسی محدود بسازید و `DATABASE_URL` را در تنظیمات خصوصی backend تعیین کنید:

```dotenv
DATABASE_URL=postgresql://USERNAME:PASSWORD@HOST:5432/DATABASE_NAME
```

این نمونه حاوی اطلاعات واقعی نیست. نویسه‌های ویژهٔ نام کاربری یا رمز باید در URL رمزگذاری شوند. سپس migrationها را روی پایگاه دادهٔ مقصد اجرا کنید. SQLite و PostgreSQL پایگاه‌های مستقل‌اند؛ تغییر URL داده‌های قبلی را منتقل نمی‌کند. انتقال داده و تهیهٔ نسخهٔ پشتیبان باید به‌صورت برنامه‌ریزی‌شده انجام شود.

برای استقرار HTTPS، `DEBUG=false`، کلید تصادفی جداگانه، میزبان و مبدا CSRF دقیق و کوکی‌های امن را تنظیم کنید. مقدار `FRONTEND_URL` را نشانی عمومی HTTPS واقعی رابط، مثلاً `https://admin.example.com/`، قرار دهید. Django را با سرور سازگار WSGI/ASGI و Next.js را با build تولیدی اجرا کنید. یک reverse proxy قابل اعتماد را جلوی هر دو قرار دهید؛ ترجیحاً رابط و `/api/` از یک دامنه ارائه شوند. فقط اگر پروکسی سرآیندهای forwarded ورودی کاربر را حذف و مقادیر معتبر خودش را جایگزین می‌کند، `TRUST_PROXY_HTTPS=true` را تنظیم کنید. `manage.py check --deploy` را برای تنظیمات استقرار اجرا کنید.

محدودکنندهٔ ورود در پایگاه داده نگه‌داری می‌شود: در پنجرهٔ ۱۵ دقیقه‌ای، ۵ تلاش ناموفق برای هر نام کاربری یا ۲۰ تلاش برای هر IP می‌تواند ورود را ۱۵ دقیقه محدود کند. شمارندهٔ حساب بین پردازه‌ها مشترک است و برای این کنترل Redis لازم نیست. IP از `REMOTE_ADDR` گرفته می‌شود و backend به `X-Forwarded-For` دلخواه اعتماد نمی‌کند؛ پشت Next.js یا پروکسی، محدودیت IP می‌تواند بین چند کاربر مشترک شود. در production، محدودسازی لبهٔ شبکه را با توپولوژی واقعی تنظیم کنید.

برای پاک‌سازی شمارنده‌های غیرفعال قدیمی می‌توانید فرمان `manage.py cleanup_login_throttles` را با Python محیط مجازی به‌صورت روزانه اجرا کنید. این کار را با Task Scheduler ویندوز یا زمان‌بند سرور انجام دهید؛ حذف دستی همهٔ شمارنده‌ها کنترل محدودسازی فعال را از بین می‌برد.

SQLite انتخاب مناسبی برای توسعهٔ محلی و استفادهٔ سبک است، اما نوشتن هم‌زمان متعدد و استقرار پرترافیک به PostgreSQL نیاز دارد. نگهبان آخرین مدیر کل در SQLite از تراکنش نوشتن و در PostgreSQL از قفل ردیف‌های مدیران فعال استفاده می‌کند؛ تغییر مستقیم داده با SQL مشمول این نگهبان نیست. برای production، پشتیبان‌گیری، نظارت، محدودیت شبکه و سیاست مدیریت کاربران را بررسی کنید. این پروژه جایگزین بازبینی امنیتی مستقل یا طراحی زیرساخت عملیاتی نیست.

## رفع اشکال

| نشانه | اقدام |
| --- | --- |
| `No module named django` | Interpreter باید همان `.venv` باشد؛ نصب `backend\requirements.txt` را با Python همان محیط انجام دهید. |
| `no such table` | در پوشهٔ `backend` فرمان `manage.py migrate` را اجرا کنید و مسیر پایگاه داده را بررسی کنید. |
| صفحهٔ ۴۰۴ در پورت ۸۰۰۰ | رابط را در `http://127.0.0.1:3000/` باز و Next.js را جداگانه اجرا کنید. نسخهٔ فعلی صفحهٔ اصلی backend را به `FRONTEND_URL` هدایت می‌کند؛ سرور Django را پس از به‌روزرسانی دوباره اجرا کنید. تغییر `DEBUG` به `false` به‌تنهایی مسیر رابط ایجاد نمی‌کند. |
| پیام «سرویس ورود در دسترس نیست» | در پوشهٔ `frontend` فرمان `npm run dev` را اجرا کنید؛ این فرمان پیش از نمایش پنل، آماده‌بودن Django را بررسی می‌کند. خطای شروع سرویس را در ترمینال و تنظیمات `backend/.env` و `DJANGO_API_ORIGIN` را بررسی کنید. در اجرای تولیدی، Django باید جداگانه فعال باشد. |
| خطای CSRF یا ورود ناموفق پس از تغییر آدرس | یک میزبان ثابت استفاده کنید؛ مقدار `CSRF_TRUSTED_ORIGINS` را همراه پروتکل/پورت بررسی کنید و کوکی‌های همان میزبان را پاک کنید. |
| هدایت ناخواسته به HTTPS در توسعه | `.env` محلی را از نمونه بسازید؛ `DEBUG=true` و تنظیمات کوکی/redirect مناسب HTTP محلی باشند. |
| پاسخ ۵۰۲ یا خطای اتصال API | Django باید روی پورت ۸۰۰۰ فعال باشد؛ `DJANGO_API_ORIGIN` و راه‌اندازی مجدد Next.js را بررسی کنید. |
| پورت ۸۰۰۰ یا ۳۰۰۰ اشغال است | پردازهٔ قبلی را ببندید؛ اگر پورت را تغییر دادید، origin رابط/API و مبداهای CSRF را هم هماهنگ کنید. |
| خطای `database is locked` | پردازه‌های تکراری و اتصال‌های باز SQLite را ببندید؛ برای هم‌زمانی بالاتر PostgreSQL را انتخاب کنید. |
| `npm ci` ناموفق است | نسخهٔ Node/npm و دسترسی به npm registry را بررسی کنید؛ lockfile را برای رفع خطای نصب حذف یا بازنویسی نکنید. |
| محدودیت ورود موقت | پس از پایان بازهٔ محدودسازی دوباره امتحان کنید؛ سرویس را برای دورزدن کنترل امنیتی مرتباً راه‌اندازی مجدد نکنید. |

## فایل‌های خصوصی و تولیدشده

`.env`، `.env.local`، `.local-secret`، پایگاه دادهٔ محلی، محیط مجازی، فایل‌های بارگذاری‌شده، `node_modules`، `.next`، گزارش‌ها و خروجی‌های آزمون در `.gitignore` قرار دارند. نمونه‌های محیط، migrationها، آزمون‌ها و lockfileها باید در Git بمانند. پیش از هر commit، خروجی `git status` را بررسی کنید.
